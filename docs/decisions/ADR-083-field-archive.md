# ADR-083：抢修档案（断纤事件、同缆组）与未解决问题库

## 状态

已接受（2026-10-10）。

## 背景

每次断纤抢修的信息（哪些口一起断、何时恢复、验收结果）没有沉淀，下一次只能重新判断；同一条主干光缆上的几个口经常一起断，但系统无从得知。Pi Agent 答不上来或答错的问题也没有被收集，无法补充。

## 决策

1. **断纤识别**（`src/outage-events.mjs`）：夜间采集每台 OLT 后按 PON 口判断——整口 ≥80% ONU 离线为“进行中”；中兴 C300 额外读取最后离线时间与原因，同口 ≥3 户且 ≥60% 在 36 小时内同一 10 分钟窗口因 LOS/LOF 离线、且当前已有在线户，记为“已恢复”的断纤并带上断纤时间。飞书村级抢修查询发现的整口离线口也记为断纤。恢复后的口自动关闭未结束的记录。
2. **事件与验收存档**：开始时间相差 30 分钟以内的记录归为同一事件；飞书抢修验收结果（检查的口、结论、汇总数字）存档，在事件列表中关联显示。
3. **同缆组推断**：只看两个及以上口同时断的事件，两口一起断过 ≥2 次且同断比例（共同次数 / 两口断纤次数并集）≥60% 视为同缆，连通的口归为一组。推断结果为候选，管理员在“抢修档案”页确认后，飞书抢修卡片对异常或整口离线的口给出同缆提示。
4. **未解决问题**：飞书中查不到村名、无结果且 Pi Agent 未给出回答、Pi Agent 出错，以及外勤以“不对 / 没用”等开头回复时，记录（上一轮）问题并按规范化文本累计次数。管理员补答后生成已生效的 `faq` 记忆，召回时按问题文本相互包含匹配。
5. **写入通道**：飞书应用只拿到只读数据网关；抢修存档、同缆提示和问题记录通过 Electron 主进程注入的 `fieldArchiveRecorder` 写入本地 SQLite，失败时静默跳过，不影响查询回复。

## 安全边界

只使用既有 SNMP 只读查询与本地 SQLite；不新增设备命令，不改变命令白名单。

## 后果

- 同缆组需要积累多次真实断纤后才会出现；早期页面可能为空。
- 华为、C600 只能识别“采集时仍在断纤”和“飞书查询时发现的”断纤，白天断、白天修好的不会被夜间采集补记。
- 夜间采集对 C300 每口多两次只读 walk。
