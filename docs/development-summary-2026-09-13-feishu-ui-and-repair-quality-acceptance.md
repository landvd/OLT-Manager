## 1. 业务背景与用户核心诉求

在 OLT Manager 纳管 7 台 OLT、完成 1.4 万+ 条网管台账与 BOSS 数据合并闭环之后，一线装维人员在移动端（飞书群/单聊机器人）日常运维与现场抢修中提出了更高的实战化需求：

1. **反向定位需求**：
   - 装维人员在现场查看机房或 OLT 告警时，经常只有设备 IP 和槽位 PON 口（例如 `172.19.104.101 3/4` 或简写 `104.101 3/4`），需要快速反查该 PON 口覆盖的“一级地址”（光交箱、覆盖村庄或片区），以便快速出车或通知对应片区师傅。
2. **村级光功率查询实战定位重构**：
   - 用户明确提出：村级光功率查询主要用于**光缆中断抢修后，快速判断主干光纤熔接质量是否合格、损耗是否过大**。传统仅列出数字的方式无法直观定界是“主干熔接不良”还是“个别皮线老化”。
3. **飞书交互卡片视觉与可读性优化**：
   - 现场光线强、抢修时间紧，原有文字排版不够直观，需要一眼分清“良好、预警、危险”；掉电（DyingGasp）与断纤（LOS）需要强对比度徽标；联系电话需支持手机端一键点击直拨。
4. **帮助菜单场景化**：
   - 原帮助信息仅为指令罗列，装维师傅容易抓不住重点；需要按照一线真实场景（查单、抢修、智能问答、指标速查）重构。
5. **Win7 发行与 Pi 助手运行模式确认**：
   - 现场工作电脑为 Windows 7 x64，需要生成绿色免安装测试包，并明确解答“Pi 助手是否需要单独安装环境”的疑问。

## 2. 核心功能设计与实现落地

### 2.1 OLT IP + 板卡/PON 逆向定位一级地址（光交箱/村庄）
- **功能目标**：输入 `172.19.104.101 3/4` 或 `104.101 3/4` 时，自动解析出所属 OLT 与对应 PON 口，并智能提取台账中的一级地址（所属光交箱、村庄片区）。
- **实现方案**：
  1. **输入解析**（`src/feishu/production-language-provider.mjs`）：
     - 正则匹配完整 IP 或缩写 IP（如 `104.101 3/4` $\rightarrow$ 补全为 `172.19.104.101`）；
     - 结构化提取 `slot` 与 `pon`。
  2. **台账反向聚合**（`src/olt-data-gateway.mjs`）：
     - 新增 `findLedgerEntriesByPonPort` 与 `findVillageOrAreaByPonPort`；
     - 检索本地 SQLite 台账中匹配该 `olt_id` 和 `pon_id` 的所有记录；
     - 自动统计该 PON 口下关联的地址列表，提炼最高频的一级地址（如 `XX村委会`、`XX光交箱03`），并统计在线/离线用户数及光衰平均值。
  3. **输出卡片**：直接在顶部醒目标注【📍 所属一级地址：厚街镇三屯村 02 号光交箱】，秒级指引现场出车。

### 2.2 村级光功率抢修验收与主干熔接质量定界（实战重构）

- **实战业务背景与现场痛点**：
  - 用户反馈：“输入双岗村所有 PON 口（36 个口），显示最差的 3 个没意义，因为一直都是光衰减大的（常年老弱光/皮线问题），与本次主干抢修熔接行为无关；另外还有 5 个口显示未完成，但实际是正常的（东新街21号、中环大路二巷1号，还有 3 个显示未提供）”。
- **根因深度分析**：
  1. **常年老弱光误导问题**：在 36 个 PON 口的大村庄中，总有几户因入户室内皮线老化、接头沾灰而长期处于 `-28 ~ -29 dBm`。如果粗暴按绝对值挑出最差 3 户，永远挑出的都是常年老弱光，与本次主干抢修熔接质量毫无关联，严重误导现场。真正与抢修相关的是**抢修前后光衰的变化量（差值突变恶化 $\Delta$）**与**整口离线/未通光**。
  2. **“东新街21号”显示未完成的根因**：该口共有 15 户，其中 13 户为“南五村”，仅 2 户包含“双岗村”。旧代码严格按村名过滤抽样用户，若这 2 户碰巧关机离线，代码即判为“无可用在线样本”并打上“未完成”标签。但实际上，同一 PON 口共享主干光缆与分光器，该口其余 13 户全部在线且光功率正常（-19 dBm），完全代表主干熔接正常！
  3. **“中环大路二巷1号”显示未完成的根因**：该口在线抽样成功且实时光衰正常（-19.5 dBm），但由于该用户没有 7 天历史光衰记录（`status === "no-history"`），旧代码苛刻地判定 `complete = false`，强行将其打入 `incomplete`（未完成）分类！
  4. **“3个显示未提供”的根因**：该 3 个 PON 口在 `pon_ports`（Excel 台账）中未登记地址，但对应用户档案中明确包含 `广东省东莞市厚街镇双岗村官美厦新兴路` 等地址，旧代码未做回退，直接将空地址回显为“未提供”。
- **重构解决方案与评级规则**：
  1. **放弃无关的常年老弱光展示，聚焦【抢修光衰突变恶化】**：
     - 计算差值 $\Delta = \text{当前} - \text{历史}$。仅当检测到 $\Delta \le -2.0 \text{ dB}$（即抢修后衰耗突增 2dB 以上）时，才作为【⚠️ 抢修光衰突增恶化 PON 口】重点预警；
     - 若全村各口光衰平稳（无恶化突增）且当前值合格，直接给出定界结论：**“🟢 主干熔接质量优秀！全村各 PON 口抽测光衰均保持平稳（未检测到抢修后光衰突变恶化），主干接头盒可放心封盒收工！”**，彻底消除对常年老弱光的误列。
  2. **同 PON 口在线用户自动回退抽样**：
     - 若目标村匹配用户均离线，系统自动回退至该 PON 口上已有的其他在线用户抽样（同 PON 口共享物理光缆与分光器，真实反映主干衰耗），彻底解决“东新街21号”等跨村边界口误判未完成的问题。
  3. **无历史实时正常放行**：
     - 只要抽测到了实时在线光功率且在标准门限内（>-27.0 dBm），即使无 7 天历史记录，也判定为**正常通畅**，彻底消除“中环大路二巷1号”等正常口被扣上“未完成”帽子的缺陷。
  4. **用户装机地址智能提炼（消灭“未提供”）**：
     - 当 PON 台账未录入地址时，系统自动从该 PON 口已有用户的档案中提取代表性地址（如 `双岗村官美厦新兴路`），彻底杜绝卡片显示“未提供”。

### 2.3 飞书卡片视觉全面重构
- **光功率红绿灯仪表盘**：
  - 🟢 `良好 (>-24dBm)`：光路通畅稳定；
  - 🟠 `预警 (-24~-27dBm)`：边缘弱光；
  - 🔴 `危险 (<-27dBm)`：严重弱光，易频繁掉线重连。
- **高对比度离线根因大徽标**：
  - ⚡ `DyingGasp掉电`：明确标注为“用户端断电/拔电源”，排障无需出车查光路；
  - ✂️ `LOS断纤`：明确标注为“光信号丢失/光纤折断”，立即定位光路故障。
- **一键直拨电话**：
  - 在卡片内联系电话处渲染 Markdown 链接 `[138xxxx1234](tel:138xxxx1234)`，装维在飞书手机客户端点击即可直接拨打业主电话。

## 3. Pi 智能助手（Pi Agent）免安装与运行机制说明

针对用户关切的“PI助手需要安装吗？”，架构原则如下：

1. **绝对零依赖、免安装**：
   - Pi 助手属于 OLT Manager 原生内部模块（位于 `src/pi-agent/`），全部代码随客户端直接打包（如 Win7 ZIP 内的 `resources/app/src/pi-agent/`）；
   - **无需安装任何 Python 环境、Node.js、数据库或浏览器插件**。
2. **自适应“双引擎”架构**：
   - **离线确定性知识库（默认即开即用）**：
     - 在完全不配置大模型 API Key，或处于内网隔离环境时，自动激活内置的 54 条实战排障知识库；
     - 涵盖华为 MA5800 与中兴 C300/C600 的全部常用诊断命令、告警树与门限标准，毫秒级直接响应。
   - **AI 智能多步推理引擎（可选增强）**：
     - 若系统设置中配置了兼容 OpenAI 接口的 API Key（如 DeepSeek、通义千问等），自动激活 Function Calling 智能排障与联网检索能力。
