# 资源用户装机地址清洗总结

## 背景

NMSE-PON 用户资料中的装机地址可能把网格片区、小区标签或道路层级重复拼接到实际地址前。该问题只影响本机用户快照展示和查询，不涉及 OLT 配置、SNMP 写入或 NMSE-PON 回写。

## 规则边界

`normalizeResourceInstallationAddress()` 以结构而非固定村名清洗地址，并保持幂等。

- 去除末尾 `#`。
- 当“编号 + 片区”后再次出现前段地址的行政区后缀时，移除重复前缀及其中间的片区/小区标签，保留第二段实际村、道路和门牌。
- 当镇、乡或街道后出现“同名道路 + 同名村”的紧邻结构时，只移除前一段同名道路，保留村及后续实际道路、门牌。
- 连续重复前缀循环清洗至文本不再变化。
- 不匹配上述结构的正常地址保持不变；镇、街道等真实行政区不得删除。

规则覆盖正式用户快照和调试检查点。完整同步与检查点写入都在保存前调用同一规范化函数，避免下一次同步重新引入脏数据。

## 历史数据处理流程

1. 为每个新发现的结构先添加合成样例和正常地址保护样例。
2. 运行 `pnpm test`、`node --check src/db.mjs` 与 `git diff --check`。
3. 重启 Electron 桌面进程，使本机服务加载新规则。
4. 调用 `POST /api/admin/resource-management/clean-addresses`。该接口在本机 SQLite 事务内更新 `resource_user_snapshots` 与 `resource_user_checkpoints`，并刷新用户数据集版本；不连接 NMSE-PON 或 OLT。
5. 使用精确 ONU 标识确认目标记录已规范化，但验证输出只保留命中数量和布尔结果，不输出用户资料。
6. 再次调用清洗接口。返回变更数为 `0` 才可确认规则在实际存量数据上幂等。

## 维护经验

- 不要把现场中的单一村名、小区名或道路名硬编码为规则条件；应要求重复行政区或同名道路/村等可验证结构同时成立。
- 先在新同步路径中规范化，再对存量快照执行一次性清洗，二者缺一不可。
- 现场数据可能存在多层重复；清洗函数必须迭代而非只替换一次。
- 地址属于本机运行数据。测试、文档和提交中只使用合成样例，不提交真实用户、电话、ONU 序列号、OLT 地址或 SQLite 数据库。
