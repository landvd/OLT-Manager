# 2026-08-18：NMSE-PON 与网管二期合并 ONU 开发总结

## 目的与当前分支

本次工作在 `codex/nmse-ngb-merged-data` 分支完成，目标是把网管二期和 NMSE-PON 的 ONU 数据统一到本地 SQLite，并解决 ONU 坐标迁移、字段缺失、同步失败和飞书展示不一致问题。

本文件只记录脱敏的工程决策、故障经验和继续开发步骤。真实账号、密码、Cookie、token、CUID、FDN、现场用户资料和运行数据库不写入文档。

## 最终数据规则

统一数据集以网管二期为设备主数据源：

1. OLT、槽、板卡、PON 口和 ONU ID 以网管二期为准，统一主键为 `oltIp + chassis + board + pon + onuId`。
2. 网管二期设备坐标和 NMSE-PON ONU 索引按标准化坐标匹配，兼容 `1/3/12:8` 与 `1/3/12/8` 两种展示格式。
3. NMSE-PON 的唯一关联键优先使用 LOID。LOID 不变时，即使 OLT 或 PON 坐标发生迁移，也要把用户资料关联到网管二期的新坐标。
4. 网管二期设备字段为主，包括设备号、设备状态、光功率、距离、MAC、序列号等。
5. NMSE-PON 提供 LOID、用户名和来源坐标；电话、装机地址在 NMSE 有非空值时优先采用 NMSE。
6. 当 NMSE-PON 没有匹配记录，或对应电话/装机地址为空时，保留网管二期已保存的用户名、电话和装机地址，避免合并结果出现空白。
7. 无法解析坐标、重复网管二期主键、重复 NMSE LOID 或无法归属的 NMSE 记录不得猜测；保留正常网管二期行，并写入冲突记录。

## 两套源数据的保存方式

- 网管二期全量结果先写入 `merged_onu_network_snapshots`。
- NMSE-PON 全量用户资料先沿用原有链路写入 `resource_user_snapshots`，执行装机地址清洗和标准化后，再提取 LOID、用户名、电话、装机地址、ONU 索引和来源 OLT，写入 `merged_onu_nmse_snapshots`。
- 最终结果写入 `merged_onu_snapshots`，供本地 ONU 查询、用户资源管理页面和 Feishu Gateway 使用。
- 源状态、运行记录、冲突和最终 revision 分别由 `merged_onu_source_state`、`merged_onu_sync_runs`、`merged_onu_conflicts` 和 `merged_onu_dataset_state` 记录。

## 现场字段映射经验

网管二期 ONU 表的字段名称不能只按早期合成 fixture 推断。当前已确认并接入的字段别名包括：

| 统一字段 | 网管二期现场字段 | 说明 |
| --- | --- | --- |
| `deviceNumber` | `STB_SN` | 用户反馈的网管二期设备号；例如设备号为空时，先检查该字段是否已进入源快照 |
| `username` | `CUSTNAME` 等 | 网管二期用户姓名回退字段 |
| `userPhone` | `MOBILE` 等 | 网管二期联系电话回退字段 |
| `installationAddress` | `WHLADDR` 等 | 网管二期装机地址回退字段 |
| `onuIndex` | `DEVNAME`、`ONUDEVICEINDEX` 或槽/板卡/PON/ID 回退字段 | 统一为结构化坐标，并保留展示值 |

适配器必须在第一层做白名单投影，只把后续合并需要的字段交给数据库层；不能把原始远端响应、凭据、会话材料或内部标识透传到 API、日志或 SQLite。

## 同步操作顺序

### 独立同步

- “同步网管二期”：完整 SQLite 备份并校验后，只读取网管二期并替换网管二期源快照。
- “同步 NMSE-PON”：完整 SQLite 备份并校验后，只读取 NMSE-PON、保存完整用户快照、清洗后提取合并字段并替换 NMSE 源快照。
- 任一独立同步失败，都保留该系统上一次成功的源快照。

### 手动合并

“手动合并”只读取本地两套源快照，不再次访问远端系统。流程是：

```text
完整 SQLite 备份
  -> 读取网管二期源快照
  -> 读取 NMSE-PON 源快照
  -> 坐标匹配 / 唯一 LOID 迁移 / 严格坐标回退
  -> 联系人字段非空回退
  -> 记录冲突
  -> 事务替换统一快照并更新 revision
```

“全量同步”仍保留为快捷入口，按网管二期 → NMSE-PON → 合并的顺序执行。所有合并入口均拒绝 `oltId` 部分同步，避免全表替换语义误删其它 OLT。

## 主要故障与解决经验

### NMSE-PON 同步过慢或首个请求超时

现场服务端对 `pageSize=100` 不兼容，首个 ONU 列表请求可能长时间无响应。当前实现固定使用现场兼容的 20 条分页，并保留最多 8 路只读分页并发；首个分页有更长的超时和临时失败重试，分页期间遇到会话过期会重新建立只读会话并重试当前页。

判断同步是否真的完成，必须看运行状态和分页计数，不能只看 HTTP 200。HTTP 200 仍可能包含 DWR 业务异常或空业务体。

### 网管二期设备号为空

旧网管二期源快照是在加入 `STB_SN` 映射前生成的，因此代码修复不会自动补回旧快照中从未保存的设备号。处理方法是重新登录网管二期，执行“同步网管二期”，确认源快照数量和设备号非空后，再执行“手动合并”。

### 电话和装机地址为空

早期适配器未投影 `CUSTNAME`、`MOBILE`、`WHLADDR`，导致网管二期联系人字段在进入源快照前就丢失。加入字段别名后，旧数据仍不会自动恢复；必须重新同步网管二期，再手动合并或全量同步。

### 用户跨 OLT/PON 迁移

不能用旧坐标直接覆盖新坐标，也不能根据相似 IP 或末尾数字推断映射。网管二期支撑网 IP 与 OLT Manager 管理 IP 属于不同命名空间，必须使用本机已确认的 `resource_olt_ip_mappings`。ONU 迁移时用不变 LOID 关联旧 NMSE 用户资料和新网管二期坐标。

### “保存并登录”成功但同步仍失败

登录、组织树、OLT 发现和 ONU 分页是不同阶段。错误提示必须保留阶段、脱敏网络错误和分页进度；不能把所有错误压缩成“请检查登录状态、IP 映射和只读数据”。遇到失败先查看运行记录和进度，再决定是否重新登录或重试。

### 密码保存与本地 WEB 测试

- 网管二期密码可以为方便下次登录而保存，但不能保存明文。桌面版只有在用户明确勾选“本机自动登录”后，才使用 Electron `safeStorage` 保存到 SQLite 之外的操作系统加密存储。
- 纯 Web/Node 环境没有桌面系统密钥链能力，仍使用迁移主密码解锁本机加密密文；不能为了自动登录而降级成明文、写入日志、备份或 API 响应。
- 本地 WEB 默认监听 `127.0.0.1:8787`。使用 Codex 内置浏览器做页面验收，不需要使用外部浏览器自动化；页面操作只验证本地 UI 和固定只读 API，不代表远端同步已经成功。
- 页面显示“合并 ONU 数据同步失败”时，优先查看 `/api/admin/merged-onu/sync/progress` 和运行记录的阶段、分页计数、备份状态及脱敏错误，再处理登录、映射或上游超时。

## 页面与 Feishu 边界

- 用户资源管理页的“合并 ONU 数据快照”读取 `merged_onu_snapshots`，显示网管二期设备号、LOID、用户名、电话、装机地址和坐标；不再展示重复的设备名称列。
- 独立同步按钮按对应登录状态启用；手动合并不访问远端，但必须已有两套源快照。
- Feishu ONU 详情以合并快照为准；复制 LOID 只回显 LOID，不执行远端动作。
- Feishu 历史光功率只读取本地 `onu_status_history` 最近 7 天、最多 48 条，不因查看卡片触发 NMSE-PON 或 OLT 刷新。

## 继续开发/现场验收 Runbook

1. 先确认当前分支、未提交改动和本地数据库备份，不要覆盖 `data/backups/`。
2. 启动本地 Web，确认 `http://127.0.0.1:8787/api/status` 可访问。
3. 登录网管二期后执行“同步网管二期”，观察阶段、OLT 数量、ONU 总数和设备号/联系人非空计数。
4. 登录 NMSE-PON 后执行“同步 NMSE-PON”，观察完整用户分页是否完成；失败时保留源快照，不要先做破坏性清理。
5. 两套源均成功后执行“手动合并”；如只需同时更新两套源和最终表，可使用“全量同步”。
6. 在合并快照中检索已知 LOID、用户姓名或设备号，核对跨坐标迁移、联系人回退和设备号。
7. 发现字段空白时，先区分“远端原始字段为空”和“适配器没有投影字段”，再决定是否重新同步；不要只清空最终表。
8. 现场验证只允许固定只读接口，不输入或记录设备写命令，不扩展为任意 DWR/HTTP 代理。
